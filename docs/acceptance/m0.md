# M0 acceptance: the model runtime

Targets come from the blueprint ("Storage, security & first run" → Targets):

| Tier | Chat speed | First token after a model load |
|---|---|---|
| Minimum (4 GB VRAM) | ≥ 10 tokens/s | ≤ 8 s |
| Recommended (8 GB VRAM) | ≥ 30 tokens/s | ≤ 10 s (was 5 s; changed after the Windows run, see below) |

`lectern bench` checks both. It unloads every idle model, times a chat (first token, model load included), then takes the median speed of three more chats. "First token after a model load" stands in for "after a swap": in a swap, the load is what costs time.

## How to run it on a machine

```sh
uv sync && npm --prefix web ci && npm --prefix web run build
uv run lectern doctor --runners        # tier, GPU, which llama.cpp build it will use
uv run lectern serve                   # finish first run in the browser (downloads the chat model)

# in a second terminal, with the server running:
uv run lectern bench
uv run lectern dev swap-test --pages 12 --budget-mb 5000 --fake-model    # expect: swaps: 1
uv run lectern dev swap-test --pages 12 --budget-mb 40000 --fake-model   # expect: swaps: 0
```

For the CPU-only run on the 8 GB PC, start the server with `CUDA_VISIBLE_DEVICES=` so CUDA sees no GPU.

The swap-test budgets suit the minimum-tier model (Qwen3.5-4B, about 3 GB per copy). On the recommended tier, use a budget a little above one copy of Qwen3.5-9B (about 7000 MiB) for the 1-swap run.

### Windows PC, 8 GB NVIDIA (recommended tier): RTX 4060 Laptop, Core Ultra 7 155H, 16 GB RAM, Windows 11

[`m0-windows-8gb.md`](m0-windows-8gb.md); the full output and both findings are in

`lectern doctor --runners` found the tier **recommended** (8188 MiB card, 7574 MiB budget),

| Memory read from the runner log | `CUDA0 … buffer size` lines present | — | pass |

| `lectern serve` itself exits on Ctrl+C | no, hung indefinitely; **fixed afterwards**, see below | exits | fixed |

Two findings, both settled on 2026-09-29:

- **The 5 s first-token target wasn't reachable for a 9B model on this card.** llama.cpp alone
  spends 4.74 s between "loading model" and "model loaded", 3.25 s of it after all 33 layers are
  already on the GPU (context, a 512 MiB KV cache, a 201 MiB recurrent-state buffer). Lectern's
  own overhead is about 1.2 s. Nothing is misconfigured. **Decision:** the recommended-tier
  target becomes **≤ 10 s**. The load stays in the measurement, because it's what a swap costs,
  and all three runs pass it. (`TARGETS` in `src/lectern/cli.py`; the comfortable tier still says
  5 s and gets revisited when a comfortable machine is tested.)
- **`lectern serve` hung on Ctrl+C.** Uvicorn's graceful shutdown waits for every open
  connection before it runs the app's shutdown hook, and the page the app opened keeps two event
  streams open (`/api/runtime/events`, `/api/models/events`). So the process stopped serving but
  never exited. It was reproduced on macOS with SIGINT too, so it wasn't Windows-specific.
  `llama-server` did exit (it shares the console and gets the signal directly), which is why
  step 5's `Get-Process llama-server` check came back clean and hid it. **Fixed:** `lectern
  serve` now tells the app it's shutting down as soon as the signal arrives, the streams end,
  and the process exits in about 0.5 s. A 3 s graceful-shutdown timeout stays as a backstop.
  `tests/test_serve_shutdown.py` holds both streams open and sends SIGINT. Step 5 of the Windows
  guide now also checks for the app process.

A note on first-chat time: a **cold** first chat right after starting `lectern serve` took
27.6 s to its first token on this machine, against about 6 s inside `bench`. The difference is
the OS file cache. On a fresh start the 5.7 GB model file is read from disk; `bench` measures
after an unload, when the file is usually still cached. That's expected, but it's the number a
user sees first after a reboot.

The 0-swap swap test (40000 MiB budget) was not run here on purpose, for the same reason as on
the 4 GB Linux PC: it would tell the runtime the card has 40 GB and load a second copy of the
model onto 8 GB. It passed on the Mac.

### CPU only (the same 1050 Ti machine with `CUDA_VISIBLE_DEVICES=`)

Run on 2026-09-29 right after the GPU run. llama.cpp logged `no CUDA-capable device is detected`
and loaded the model on the CPU (6 threads). No speed target applies; `lectern bench` must
finish without an error, and it did:

| Check | Result |
|---|---|
| First token after a model load | 14.8 s |
| Chat speed, median of 3 | 9.2 tokens/s |
| Finished without an error | yes |

`lectern bench` printed "BELOW TARGET" because `CUDA_VISIBLE_DEVICES` hides the GPU from
llama.cpp but not from NVML, so the app still counted the machine as minimum tier and applied
its targets. A truly GPU-less machine is below-minimum tier, where no target applies.

## Also check on the Linux PCs

- **Tier detection.** `lectern doctor` reports the card's memory as NVML sees it. The tier thresholds assume an 8 GB card reports about 8188 MiB.
- **Build choice.** `doctor --runners` shows `linux-cuda13` or `linux-cuda12` to match the driver, and `installed: true` after the first chat.
- **Memory reading.** Look for `CUDA0 … buffer size` lines in `<LECTERN_HOME>/run/<model>/server.log`. The Models & memory gauge should show a figure close to what `nvidia-smi` reports for the llama-server process.

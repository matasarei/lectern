# M4 acceptance: Lectern installed, on Linux, a Mac and Windows

M4 is the installers. This file has three parts:
- **Linux** (the rest of this section, to "Not checked here"): a server, run as your own `systemd --user` service.
- **[macOS](#macos-the-menu-bar-app):** the menu-bar app, run on the Mac these docs are written on.
- **[Windows](#windows-the-tray-app):** the tray app; a runbook, to be run by hand on a Windows PC.

On Linux, M4 is the server install:
- **Part 1, the app behind something:** `LECTERN_PUBLIC_URL` tells Lectern the address it's reached by, so a proxy or a tunnel can sit in front of it. `lectern url` prints the access link on a machine with no browser.
- **Part 2, the install:** `./install.sh` puts Lectern in `~/.lectern` as your own service (`systemctl --user`), with no sudo. Running it again is the update. Docker is the option.

The automated checks are recorded below. **The real run hasn't happened yet:** its commands are here, and its tables fill in from their output.

## What M4 asks, and where it's checked

| Asked | Checked by |

| The service is back after a reboot, with nobody logged in | B |

| A failed install leaves the old version running; `uninstall.sh` with and without `--purge` | B |
| The Docker image serves Lectern with the GPU | B |

## How to run it

There are two runs, for two kinds of machine:
- **A** is for a machine that already runs Lectern and is in use. Nothing is rebooted, removed or installed fresh. The update restarts Lectern's own service and nothing else.
- **B** is for a machine that may be rebooted and wiped.

**Before pasting any output:** the service's log holds the access link, which is the only lock while there's no login. The commands below leave it out (`grep -v 'token='`, and no `systemctl status`, which prints the last log lines). `lectern url` and `~/.lectern/bin/lectern-url` print it on purpose: don't paste those.

The commands use the default port, 8765. With another `LECTERN_PORT` in `~/.lectern/lectern.env`, use that one.

### A · Update in place, on a machine in use

Run it when no chat or OCR job is going: the update restarts Lectern, and a job cut by a restart stays paused until you resume it.

**1. Before the update.** The machine, the version in use, and a record to compare the data against:

```sh
hostnamectl | grep -E 'Operating System|Kernel|Hardware'
nvidia-smi --query-gpu=name,memory.total,memory.used,driver_version --format=csv,noheader
curl -s 127.0.0.1:8765/health; echo
git -C ~/.lectern/src log -1 --format='%h %ad %s' --date=short
readlink ~/.lectern/app/venv

(umask 077; sha256sum ~/.lectern/lectern.env ~/.lectern/data/token > ~/m4-kept.sha256)
ls ~/.lectern/data/users/*/projects | wc -l
du -sh ~/.lectern/data/models
```

**2. The update.**

```sh
cd ~/.lectern/src && git pull && time ./install.sh
```

It should end with "Upgraded to Lectern … and restarted it." and the next steps. If it says the new version didn't start, it also prints how to go back: stop here and send that output. The `journalctl` line it suggests prints the access link too: add `| grep -v 'token='` before pasting what it shows.

**3. After it.** The new version answers, the data and settings are the same files, and the service is set to start at boot:

```sh
curl -s 127.0.0.1:8765/health; echo
git -C ~/.lectern/src log -1 --format='%h %ad %s' --date=short
readlink ~/.lectern/app/venv                  # a new folder
ls ~/.lectern/app/versions                    # two: the new one and the one before it
sha256sum -c ~/m4-kept.sha256                 # both: OK
ls ~/.lectern/data/users/*/projects | wc -l   # as before
du -sh ~/.lectern/data/models                 # as before
systemctl --user is-active lectern; systemctl --user is-enabled lectern
loginctl show-user "$USER" -p Linger
systemd-analyze --user verify ~/.config/systemd/user/lectern.service
journalctl --user -u lectern --since "-10min" --no-pager | grep -v 'token=' | tail -30
```

**4. What Lectern sees, and the chat's speed.** `bench` unloads Lectern's idle models first, then times four chats:

```sh
(
  set -a; . ~/.lectern/lectern.env; set +a
  ~/.lectern/app/venv/bin/lectern doctor --runners
  ~/.lectern/app/venv/bin/lectern bench --port "${LECTERN_PORT:-8765}"
)
nvidia-smi --query-gpu=memory.used,memory.total --format=csv,noheader
```

On a 4 GB NVIDIA card `doctor` should say tier `minimum` and a `linux-cuda…` build, and `bench` should end with `PASS` (first token ≤ 8 s after a load, ≥ 10 tokens/s).

**5. A scan to DOCX, from one message.** First, in a terminal on the server, follow what the runtime does, with the time on every line. Leave it running through steps 5 and 6:

```sh
printf 'X-Lectern-Token: %s\n' "$(cat ~/.lectern/data/token)" \
  | curl -sN -H @- 127.0.0.1:8765/api/runtime/events \
  | while IFS= read -r line; do case "$line" in data:*) printf '%s %s\n' "$(date +%T)" "$line" ;; esac; done \
  | tee -a ~/m4-runtime.log
```

It prints the state once, then a line for each thing the runtime does; a quiet runtime prints nothing. Ctrl+C stops it, and starting it again adds to the same log.

(The token reaches `curl` on its input, not as an argument, so it never shows in the process list and no copy of it is left in a file.)

Then, in the browser, from another computer and through whatever you normally reach Lectern by:
1. Open a new project and attach a one-page scan (a photo or a PDF).
2. Send: "Read the scan and prepare DOCX from it". Allow each card.
3. Watch the chat's OCR line and the OCR tab until the DOCX tab opens. Answer the questions if there are any.

Note down, as you watch:
- whether "loading the OCR model…" and "loading the chat model to clean the text…" show, and for roughly how long;
- whether the step in progress spins, in the chat's line and in the OCR tab;
- the page's reading time, as the OCR tab shows it ("read by … in … s");
- whether the DOCX came only after the questions were answered (or at once, with none);
- anything that sat still with no sign of what it was waiting for.

The swap and cleaning times come from `~/m4-runtime.log`: `loading` → `loaded` for each model, and the chat model's `lease` → `release` after it's loaded again.

**6. Twelve pages.** With the stream from step 5 still running, print the swaps so far, in a second terminal:

```sh
grep -o '"swaps": [0-9]*' ~/m4-runtime.log | tail -1     # the count since Lectern started
```

Then import a 12-page scanned PDF in the same project, open it, and press "Open as OCR session" (M2b's was the four sample pages, three times over). When it's done, run the same line again: the session's swaps are the difference between the two.

M0's swap test, which only read pages, counted one swap for 12. From the code, a session whose pages are also cleaned swaps twice: the chat model makes room for the OCR model, then the OCR model makes room for the chat model that cleans. What matters is that the number doesn't grow with the pages. Record what it is.

**7. Send back:** the output of steps 1–4, `~/m4-runtime.log`, the notes from step 5, and how you reached Lectern from the other computer (a tunnel, nginx, or directly).

### B · A machine that may be rebooted and wiped

Not for a machine in use. These commands come from the installer and the README; none has been run for real yet.

**1. A fresh install, as a normal user:**

```sh
git clone https://github.com/matasarei/lectern.git ~/.lectern/src
cd ~/.lectern/src && time ./install.sh
curl -s 127.0.0.1:8765/health; echo
systemctl --user is-active lectern; systemctl --user is-enabled lectern
loginctl show-user "$USER" -p Linger
systemd-analyze --user verify ~/.config/systemd/user/lectern.service
ls ~/.lectern
```

Note whether lingering turned on by itself or the installer printed the `sudo loginctl enable-linger` line, and whether it printed the `usermod` line for the `render` group.

**2. nginx in front, on the local network.** As the README's "Reaching it from other computers" says: copy `packaging/linux/nginx-lectern.conf`, set its `server_name`, `sudo nginx -t && sudo systemctl reload nginx`, the SELinux line on Fedora, then `LECTERN_PUBLIC_URL` in `~/.lectern/lectern.env` and `systemctl --user restart lectern`. From another computer, with the link from `~/.lectern/bin/lectern-url`:
- the first-run page loads, and the chat model downloads with its progress moving;
- a chat answers, and the reply appears as it's written;
- steps 4–6 of run A.

**3. A reboot, with nobody logged in:**

```sh
sudo reboot
# from the other computer, before logging in to the server again:
curl -s http://SERVER/health; echo      # SERVER: the name or address nginx answers on
# then log in:
uptime -s; systemctl --user show lectern -p ActiveEnterTimestamp   # started at boot, before this login
```

Then send one chat message and check the model is on the GPU: `nvidia-smi --query-compute-apps=name,used_memory --format=csv,noheader` lists `llama-server`.

**4. A failed install leaves the old version running.** An empty file with a wheel's name can't be installed:

```sh
cd ~/.lectern/src
: > /tmp/lectern_ai-0.0.0-py3-none-any.whl
./install.sh /tmp/lectern_ai-0.0.0-py3-none-any.whl     # "…failed (see above); the version in use is unchanged."
curl -s 127.0.0.1:8765/health; echo                     # the same version as before
```

**5. Uninstall, last:**

```sh
cd ~/.lectern/src
./uninstall.sh && ls ~/.lectern            # data, lectern.env and src stay
./install.sh                               # back, with its projects and models
./uninstall.sh --purge && ls ~/.lectern    # only src
```

**6. Docker with the GPU,** if the NVIDIA Container Toolkit is on the machine: the four commands under "Or in Docker" in the README, then one chat message and the `nvidia-smi` line from step 3.

## macOS: the menu-bar app

### How to run it

```sh
#   a project, import a scanned PDF, ask "Read the scan and prepare DOCX from it."
git pull && make install                       # the update in place, the app open
```

## Windows: the tray app

`install.ps1` puts Lectern in `%USERPROFILE%\.lectern` and its tray app in the Start menu and the Startup folder (README "Install on Windows"). From a Mac the tray app is only compiled, as C# 5, and the scripts only analysed (`tests/test_packaging.py`). The runbook below was run on the RTX 4060 laptop of the M0 run on 2026-10-29: [results](#results-rtx-4060-laptop-core-ultra-7-155h-16-gb-windows-11).

### How to run it

In PowerShell, as yourself (not as administrator). Paste each block's output back; **leave out any line with `#token=`**.

**1. Install from a clone.**

```powershell
winget install Git.Git OpenJS.NodeJS.LTS      # then open a new PowerShell window
git clone https://github.com/matasarei/lectern.git $HOME\.lectern\src
cd $HOME\.lectern\src; powershell -ExecutionPolicy Bypass -File install.ps1
Get-ChildItem $HOME\.lectern, $HOME\.lectern\app | Select-Object FullName
Get-Item $HOME\.lectern\app\venv | Select-Object LinkType, Target
```

Expected: "Lectern <version> is installed and running."; a tray icon by the clock; `venv` a `Junction` into `app\versions`.

**2. The tray menu, item by item.** Right-click the icon:
- the first line says "Lectern is running · <version>";
- **Open Lectern** opens the browser, signed in: finish the first run (the 9B model on the 8 GB card);
- **Show Log** opens `%LOCALAPPDATA%\Lectern\Logs\lectern.log`: no line with `#token=`;
- **Stop**, then **Start**, then **Restart**: the first line follows; Lectern answers again after each;
- a left click shows the same menu; opening Lectern again from the Start menu opens it in the
  browser;
- the icon is a book in the taskbar's light or dark, closed while starting, open once Lectern
  answers; switching the Windows mode switches the icon and the menu with it.

**3. Nothing left behind on Quit.**

```powershell
Get-Process lectern, python, llama-server -ErrorAction SilentlyContinue | Select-Object Name, Id, Path
# Quit Lectern from the menu, wait for the icon to go, then:

```

Expected: the second list is empty. Then the same with the tray app ended in Task Manager (Details → Lectern.exe → End task): nothing left either.

**4. Sign out and in again.** Lectern starts by itself (the Startup folder), without a browser window.

**5. Chat and OCR on the 4060.** In a project: a chat answer (the speed line under it), then a scanned PDF of about 12 pages, "Read the scan and prepare DOCX from it." Note the swaps, reading and cleaning per page, and that the DOCX opens.

**6. The sandbox, with Docker Desktop running.** "What's 17% of 2,409.50? Compute it." The first time asks to build the image; then the answer comes from `code.run`.

**7. Update in place, Lectern running.**

```powershell
cd $HOME\.lectern\src; git pull; powershell -ExecutionPolicy Bypass -File install.ps1
```

### Results: RTX 4060 Laptop, Core Ultra 7 155H, 16 GB, Windows 11

Run on 2026-10-29 at `369cc63`: Windows 11 Pro 10.0.26300 (Russian locale, code page cp1251), NVIDIA driver 610.62, Docker Desktop 29.6.1, llama.cpp `b11236` `windows-cuda13`. So that the installed Lectern kept its data, steps 1, 8 and 9 ran on a second install (`LECTERN_DIR` in `%TEMP%`, its own `lectern.env` with port 8775, a clone of the same commit); steps 3 and 5 to 7 on the installed one.

**A tray-started Lectern freezes at its first model load, so as installed on Windows no model ever runs.** The tray app starts `lectern serve --stop-on-stdin-close`, whose `stdin` thread waits in a blocking read on the pipe (`cli.py`, `_stop_when_closed`). Every model load reads the GGUF header first (`runtime/planner.py` `read_shape`, from `wiring.py` `resolve`), which imports `gguf` and with it numpy, on the event loop. On Windows the DLL loader, running numpy's bundled OpenBLAS's start-up, then waits for the standard-input handle the read holds: the server answers nothing, `/health` included, at 0 % CPU, until Quit closes stdin (the import finished, and the model's run folder appeared, in the second Quit closed it). Seen twice through the tray; `py-spy dump --native` showed the main thread in `LdrLoadDll` → `libscipy_openblas64_` → `RtlEnterCriticalSection`. Outside Lectern, with the same Python and numpy, a thread reading a stdin pipe makes `import numpy` wait until stdin is closed (19.6 s, the probe's timeout), against 0.1 s without it; `pypdfium2` and Pillow import either way. Steps 5 and 6 were therefore run with `lectern.cmd serve`, which has no stdin thread, on the same data and port.

**Fixed the same day** (branch `fix/windows-tray-stop-event`): the tray app stops Lectern through a named event, `serve --stop-event` (`core/winevent.py`), and leaves its standard input unset; and the planner reads a model's shape with a header reader of its own (`runtime/gguf_header.py`), not gguf's, which had taken 9.48 s over the 9B's tokenizer (0.05 s now; 3.00 → 0.05 s for PaddleOCR-VL, 5.69 → 0.05 s for the coder; the same shapes). Installed with `install.ps1` and run through the tray: the 9B answered at 38.8 tokens/s, first token 20.7 s (a cold load); `py-spy` showed a "stop-event" thread and none reading stdin; Quit with the 9B loaded: everything gone in 2.7 s, "Shutting down … Application shutdown complete". During that first load `/health` went unanswered for about 8 s, gguf's reader still in place; with the header reader, installed again: `/health` answered all 160 polls (every 0.5 s, through the 9B's load), and the cold first token came in 10.5 s (39.3 tokens/s).
